# R1 enterprise ownership and site-scoped data review

Status: reviewed migration *design*, not a backfill execution result. **No production data was inspected, modified or certified.**

## 1. Current facts and severity

Existing `blueprint_site(blueprint_id PK,site_id)` explicitly maps each Blueprint to one Site, and the Studio API calls `requireOwner`. Business transitions also check ownership. However, the database schema has no verified composite FK preventing historical `blueprint_approval`, `plant_activation_set`, or `blueprint_view_layout` from naming a different `site_id` for the same `blueprint_id`. Legacy `blueprint_head` and `blueprint_revision` do not independently store `site_id`.

Additional cross-site risks:
- `site.active_set_id` may point across sites unless guarded; application checks exist, but DB-level FK/unique ownership constraints are still needed.
- `plant_activation_set.previous_set_id` and `restored_from_set_id` may cross sites or be orphaned.
- `blueprint_view_layout.layout_json` can contain equipment IDs not present after a revision migration; active editor must handle stale layout separately.
- Existing production default should run with `spring.jpa.hibernate.ddl-auto=validate`; `update` is for local development only. DB migrations need a versioned runner (Flyway/Liquibase) or a controlled DBA process, never silent schema changes.
- Dev-local `X-Zavod-Dev-Write` and browser-selected persona are NOT enterprise authorization; introduce OIDC/JWT and an organization/site ABAC boundary.

## 2. Dry-run before any write

Run `scripts/sql/r1-site-owner-audit.sql` on a **restored production backup** with a read-only DBA account; then repeat on a transactionally quiesced production database at the deployment gate. Collect counts and explicit orphan Blueprint IDs. Do not log private enterprise data into public CI.

A zero anomaly audit is required for ownership and cross-site references. For older data without `blueprint_site`, every proposed owner must be resolved from an authoritative signed site inventory. **Do not infer an owner solely from the most recent activation, layout, or approval; those may already be corrupted.** Any disputed or unknown owner goes to quarantine and blocks migration.

## 3. Human-approved manifest (explicit, not autogenerated)

`migration_blueprint_owner_manifest` is created in the maintenance environment by DBA from signed evidence, with:
```sql
CREATE TABLE migration_blueprint_owner_manifest (
  blueprint_id varchar(36) PRIMARY KEY,
  site_id varchar(64) NOT NULL,
  evidence_reference text NOT NULL,
  proposed_by text NOT NULL,
  approved_by text NOT NULL,
  approved_at timestamptz NOT NULL,
  CHECK (btrim(evidence_reference) <> ''),
  CHECK (btrim(proposed_by) <> ''),
  CHECK (btrim(approved_by) <> ''),
  CHECK (proposed_by <> approved_by)
);
```

The operator loads it using a separately reviewed CSV or explicit INSERT and verifies source-record checksum, origin, ticket and approvals. The manifest should be immutable and archived with deployment evidence; this script assumes the table exists and does **not** auto-assign or manufacture approvals.

## 4. Controlled execution

1. Backup/restore rehearsal and verified RPO/RTO. Freeze writes; capture before counts and signed inventory manifest. Confirm reviewer and operator are different people.
2. Preflight audit; resolve every orphan or contradictory row. Compare manifest site assignments with historical approval, activation and layout site IDs. Abort if unresolved.
3. Run `scripts/sql/r1-site-owner-backfill.sql` on the restored clone. It acquires transaction advisory and table locks, inserts only missing `blueprint_site` assignments, rejects pre-existing site-owner conflicts, and rolls back on postcheck failures.
4. Review diff and all invariant checks. Run on production only in approved window; record manifest hash, database snapshot ID, SQL version, row counts, operator, reviewer and approval ticket.
5. Rerun audit; only after all zero counts proceed to new FK constraints under separate additive schema migration and `ddl-auto=validate`.
6. Rollback: before commit, automatic transaction rollback; after commit, **do not blindly DELETE** site ownership or rewind append-only business history. Restore from verified backup under approved DBA incident plan. Keep site assignment manifest and audit trail.

## 5. Independent readiness gates

- B1: all Heads assigned exactly one site, no orphan revisions/approvals/layout/activations, all active/previous/restore pointers same-site.
- B2: source evidence signed and two-person reviewed; quarantine has zero unresolved assignments.
- B3: dev-local origin/header cannot authorize production endpoints, server-side OIDC + organization/site ABAC implemented and tested.
- B4: R1 BCQ-G4 operational integrity (commands, ledger and unknown-commit reconciliation) accepted; real PostgreSQL failure injection passed.
- B5: proven Spring Boot/PostgreSQL/Chromium E2E with multi-line graph+layout CAS; accessibility and independent process rules qualified.
- B6: migrator is repeatable and cross-site negative tests tested on a production-shaped clone; FK and `ddl-auto=validate` independently qualified.

**Do not merge backfill SQL as a production deployment step** until B1/B2 and independent DBA/security review are complete.
